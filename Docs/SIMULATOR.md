# Software simulator and communication foundation

The simulator is an in-memory, multi-device, half-duplex RTU software model. It does not implement a virtual COM driver or open hardware. It constructs actual FC03 request/response bytes and validates response CRC, function, address and lengths. The same BusEngine scheduling interface is used for simulated and read-only physical transports.

Each device has an independent register dictionary, identity, changing sine-wave measurement, status and relay state. LEL, BTU and FID use separate profile definitions. FID unit mode is explicitly configured because its UNITS register address is absent from the supplied manual. Simulated PDU addresses use the explicit per-device offset (-1 by default); that assumption is not hardware evidence.

Fault injection supports timeout, corrupted response CRC and Modbus exception. Recovering a device removes the fault; subsequent scheduled reads reconnect its displayed state. Retries are future polls with capped exponential per-device backoff (up to60s), not immediate repeated requests. Healthy analyzers continue to be serviced. Aggregate bus capacity and slow diagnostics mean16 devices are not promised1Hz refresh. A primary read is1..4; safe ancillary blocks are slower and identification refreshes every60s.

Simulator-only configuration has documented access/range/role checks and actual simulated readback. Simulator-only command API accepts only the reviewed allowlist and confirmation, respects calibration lock, clears register8, and models zero/span/purge/end stages. Stages last2 seconds for software tests; these times are deliberately NOT claimed as analyzer timing. Simulated alarm thresholds do not model all hardware latch behavior. Save/ack/lock behavior is illustrative; no physical success criteria are established. No control GUI is included at the monitoring milestone.

The physical adapter is PyModbus/PySerial,8N1 with retries0, default timeout0.5s. Opening it requires explicit hardware authorization and an addressing review; the initial GUI has no path to it. FID physical reads are blocked because the protocol section is missing. There is no physical write or command API. It is tested using fake clients only. CRC counts represent captured complete matching corrupt frames; fragmented/unidentifiable garbage may be classified as timeout, not proof of a CRC failure. Raw traffic is bounded to500 entries.

Tests cover exact conversions, signed endpoints, address-zero prevention, page boundaries, aliases, safe ranges, bus serialization under concurrent callers, total traffic pacing, CRC/protocol handling,16-device isolation/recovery, simulator configuration validation, lock/command exclusion, and mocked serial reconnect/close. None of these tests validate electrical RS485 behavior, USB converter timing, actual firmware commands or physical compatibility.
