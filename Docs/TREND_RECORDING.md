# Independent Trend window and recordings

Use **Open Trend** on the main toolbar. The Trend is a separate, non-modal Windows window with its own minimize, maximize, resize and close controls. Open Trend raises the existing window. Move it to another connected monitor using its title bar. Position and size are saved in `trend-window.json` beside the application data files; a disconnected monitor's saved position is brought back onto an available screen. Closing Trend hides it without stopping polling or recording. Closing the main HMI closes Trend and ends the active session.

The main Gauge screen has no embedded graph. Live trends and History / CSV navigation retain launch pages for the independent window. Existing continuous-monitoring history and its displayed-data CSV export remain available in its **Legacy monitoring history** tab. Existing accounts, commands and physical write restrictions are unchanged.

## Recording controls

The permanent **Recording Parameters** section is shown above the plot tabs. It lists eligible changing measurements from the current analyzer's GAUGES menu with one checkbox each and **Select All / Clear All** buttons. The list adapts to LEL670, LEL700, BTU and FID. A new profile defaults to its main measurement; each profile's last checkbox selection (including an empty selection) is saved independently. Existing recording sessions and their parameter metadata are unchanged.

The chooser excludes STATUS [2], LOW FLOW / SET VAC [23], SET TEMP [24], PEAK HI [38], PEAK LOW [39], CHK FLOW [42] and OUTPUT READING [50] wherever those registers occur. Saved choices are trimmed on load; if only removed channels were checked, the resulting empty selection leaves Start disabled until a new measurement is selected. Old sessions containing these channels remain viewable and exportable. STATUS and communication quality are always retained as metadata; STATUS is no longer a selectable trend channel.

Select parameters, choose1/2/5/10 seconds, then press **Start Recording**. It submits the selection and interval together and starts on the current acquisition cache without another dialog. With no checked parameters, Start is disabled. Parameter selection, interval and recording mode are locked while a session is active, paused or awaiting Start acknowledgment. **Stop Recording** ends/disarms the session and re-enables these controls after acknowledgment. The worker also rejects parameter/interval changes during a session, so a stale UI action cannot change its metadata. A profile change before a pending Start is fulfilled requires reviewing the new profile before starting.

- **Manual** is the default. Start Recording starts a new session on the next current analyzer snapshot. Stop Recording ends it. Starting again creates a separate session.
- **Automatic** starts a new session when communication is established, pauses during loss/staleness and resumes that same session after recovery. Stop Recording disarms automatic recording until Start Recording is pressed or Automatic is selected again.
- Capture intervals are **1, 2, 5 or 10 seconds**, default1. The interval limits recording capture; it does not change Modbus polling. If the analyzer is polled every2 seconds, a1-second recording interval cannot create additional1-second measurements. Cached values already captured in the session are not written again.
- Use the checkboxes for any combination of the primary measurement, measured temperatures, flow/vacuum and other eligible GAUGES readings. Calibration-menu and alarm-setting cards added to the main HMI are not automatically added to GAUGES recording. Parameter names, units and conversions come from the existing670/700/BTU/FID profiles. BTU/FID hardware/units limitations still apply. The previous all-versus-main-only toggle is replaced by these checkboxes.
- Stop before changing interval or parameter selection; each subsequent Start creates its own session with the selected metadata. Manual recording ends on an analyzer identity/profile/endpoint/unit/full-scale change and requires Start Recording again. Automatic recording starts a separate session for the new stream using that profile's saved selection. An empty selection cannot start a session.

The Trend shows state, elapsed session time (including pauses) and captured-frame count. Recording settings are saved in the existing settings file. The Manual preference does not automatically restart an old session after application restart. Automatic starts a new session after identification. An interrupted session remains queryable with an empty end time rather than an invented shutdown time.

## Timestamp and quality rules

Acquisition time is stamped on the polling worker when each register block returns. Recording consumes those cached snapshots on a separate thread, with no transport reference, reads or commands. Each value retains its response timestamp. Values originating from the legacy fault LCD use the actual LCD-response timestamp. The unique `(session, register, acquisition timestamp)` key prevents repeated cache samples from appearing as new acquisitions.

Frames are sparse: a parameter absent from a frame has no new observation at that capture. This is different from a new observation whose value is unavailable. No forward fill, interpolation, numeric clamp or held-gauge substitution enters recordings. Communication loss produces one gap frame without measurements; recovery produces a marker and the next fresh observations. STATUS has its own source timestamp, and communication quality and per-parameter quality are retained. Existing instrument faults remain visible and do not create healthy-quality data.

## Historical viewing and CSV

Open **Recorded sessions**, refresh the list, choose the session, check one or more **Historical parameters**, then **View recording**. The parameter menu stays open for multiple checkbox changes and includes Select All / Clear All. It lists only channels with saved observations in that session, including historical channels no longer offered for new recordings. This selection is independent of Recording Parameters above the tabs. A session with no saved observations has no historical choices.

Sessions are sorted newest first. Labels show a readable start time (for example `Oct 26, 2026 — 8:18:56 PM | LEL 670 / SNR671 | Hardware | 1 sec`), elapsed start-to-end duration and saved sample-frame count. Gap-only frames are excluded from that count. Active/interrupted sessions show their last saved sample duration and remain marked active / unfinished. The full label is available as a tooltip and in the session details.

**Display timezone** defaults to the Windows PC's local timezone. Select UTC or another named zone to adjust the Trend display; the preference is saved without changing Windows settings. Session labels, live/recorded time axes and export-range controls follow this choice. Historical daylight-saving rules are applied per timestamp. Axes show HH:mm:ss, adding the date across days; repeated daylight-saving wall times receive an offset to distinguish them. Storage timestamps remain UTC and existing recordings are never rewritten for display.

Different engineering units use separate vertically stacked plots inside a scroll area, with linked time axes. Channels sharing a unit share a plot and legend. Mouse-wheel zoom and drag pan remain available. Y limits fit the saved values with margins, retaining negative readings; LEL plots include a prominent zero reference. Saved observations always have visible markers. Lines require at least three consecutive numeric observations, so one/two-sample runs stay as individual points. Communication/unavailable markers break the line. The display is bounded to the first50,000 observations per session/parameter and says when this limit applies; CSV export is not bounded by the plot limit.

Export CSV offers:

1. Current recording session, or the latest session recorded in this application run after Stop. This lets the operator use Start → Stop → Export CSV directly.
2. Selected previous session.
3. All recording sessions within a **capture-time range** entered in the selected display timezone; range bounds are converted to UTC for the existing export query.

Choose a destination in the standard Windows Save dialog. The default name follows `PREVEX_LEL670_YYYY-MM-DD_HHMMSS.csv` (profile and local filename time vary). CSV uses UTF-8 BOM, comma separation, CRLF records and quoted fields. Export timestamps retain their unambiguous UTC ISO8601 values and timezone offsets regardless of the display preference. Headers identify parameter names and engineering units. Base columns include session, profile, model, firmware, analyzer identification, source, session start/end, interval, capture UTC, STATUS, STATUS acquisition UTC and communication quality. Each measurement has value, acquisition UTC and quality columns. Unavailable/unobserved fields are blank; negative numeric values remain signed numbers. Different profiles or units receive separate named columns, and each row retains its session and source metadata.

In Excel, if the local installation presents its Text Import Wizard, select **Delimited**, **UTF-8 /65001**, and **Comma**. No regional Windows or Excel settings need to be changed. Analyzer-supplied identity text is escaped when it could be interpreted as a spreadsheet formula.

Export streams read-only SQLite queries on a separate thread. It writes a temporary file beside the chosen destination and replaces the destination only after success. A failed export preserves an existing destination and does not stop polling or recording. Concurrent export sees a consistent snapshot of each selected session; observations arriving after that snapshot are available on a later export.

## Manage recorded data and retention

Open **Manage Recorded Data** in the Trend window. The non-modal window lists local recording time, analyzer/model and identification/source, duration, saved numeric sample-frame count, estimated session storage, Keep protection and completed/unfinished state. SQLite size includes the main file and WAL/shared-memory sidecars; session estimates include row payload/overhead and do not exactly apportion SQLite indexes/free pages. Use Refresh after recording or maintenance changes. Existing UTC timestamps are preserved.

The default retention period is **30 days**; alternatives are **90, 180 and365 days**. Automatic cleanup is **off initially**. An Administrator must explicitly apply a policy; enabling it confirms permanent automatic deletion. The policy persists in `recording-retention.json`. Cleanup is scheduled shortly after startup, then hourly; busy/error cases defer and retry after a minute. A session expires only when its completed end time is strictly before the UTC cutoff. Active/unfinished sessions and Keep sessions are excluded. Continuous recording defers cleanup until recording is stopped, including communication-paused sessions. This retention applies only to recording sessions/frames/values, leaving legacy monitoring retention, events, command audits and user accounts unchanged.

Only current **Administrator** accounts may change the policy, mark/remove Keep, delete sessions, create full database backups or optimize size. Authorization is checked again on the database job thread before changes. Guest/Viewer/Operator users can inspect the manager and export CSV. Keep protection remains after restart. Remove Keep requires confirmation; protected sessions must be unprotected before manual deletion too.

Select one/multiple rows and choose **Delete selected**, or use **Completed before** and **Delete older recordings**. Both routes preview the eligible count/estimated size and require confirmation. Protected/unfinished sessions are always excluded. **Export selected CSV** saves one session with a Windows Save dialog, or multiple separate CSV files to a selected folder. Export uses the existing UTC, engineering-unit and quality columns. No deletion follows export automatically.

**Create verified SQLite backup before manual deletion / optimization** is checked by default. Choose a backup folder after confirming the operation; cancelling or a backup failure cancels deletion/optimization. Automatic retention does not create backups; export/back up important data and mark Keep before enabling it. Back up databases also works separately during recording. SQLite's online backup API captures each database consistently, including committed WAL contents, and validates it with quick_check. Backups have unique UTC filenames, require estimated temporary free space and time out after120 seconds if a continually changing database prevents completion. Each database backup is its own snapshot. Keep these backups separately; to restore, close all HMI instances and preserve the current data folder before replacing a recording database with its verified backup.

Deletion is transactional per session: measurements, frames, metadata and a persistent deletion-ledger entry are committed together. A failed transaction preserves that whole session; earlier sessions in a batch may already have completed deletion. Recording/CSV/history/backup jobs coordinate with maintenance so active recording and exports are never deleted underneath. New recording requests wait visibly for current maintenance to finish. Polling remains on its existing thread/bus owner; legacy history observations are temporarily buffered with their original timestamps during cleanup and flushed afterward. This buffer is bounded at100,000 observations; an overflow fails legacy logging closed with a warning instead of interrupting polling. Confirmed controller actions and pending verification defer cleanup; new actions during maintenance are rejected before transmission and require a new review/confirmation afterward.

Deletion frees SQLite pages for reuse but may not immediately shrink the file. **Optimize database size** performs WAL checkpoints, VACUUM and quick_check in a background job. Stop recording, disconnect monitoring and finish current exports/backups first: monitoring uses the same SQLite files. Active/unfinished sessions also prevent optimization conservatively. The job checks free space on the database and OS temporary volumes (twice the allocated database size plus16 MiB), handles SQLite/disk errors, and never changes measurement timestamps. A new Connect request waits for maintenance to finish. Close other HMI instances and external SQLite readers before optimizing; they can keep checkpoints or maintenance busy.

Keep/deletion/VACUUM records are retained in each database's `recording_maintenance` ledger; deletion entries retain the removed session identification/times. Policy, backup, deletion requests/completion and errors also appear in `recording-maintenance.jsonl` beside the databases. These logs and existing unrelated histories are not deleted by session retention. Maintenance never sends analyzer commands.

## Storage and failure behavior

Recording tables extend the existing `simulation.sqlite3` and `hardware.sqlite3` files. Sessions, captured frames and per-parameter observations are separate from legacy measurement-history retention. Existing90-day measurement cleanup does not delete recording sessions. There is no direct CSV writing during collection.

Recording storage errors, including full disk, stop/disarm recording and show an error; committed data remains available. Resolve storage and explicitly start again. There is no hidden retry or successful-recording claim after a storage failure. Legacy history storage failures also leave polling active, while audit-dependent commands fail closed until reconnect. SQLite lock waits in the monitoring and recording paths are bounded. Export errors appear in Trend. Application shutdown stops acquisition and closes the active recording; an unwriteable shutdown may leave its metadata marked unfinished.

No Modbus write is sent by any Trend, recording, historical-view or CSV operation. Simulator tests do not establish physical analyzer compatibility.
